### Theme A — "A list where a property was meant"

The defect shape this retrospective was called to examine. A rule is written as an
**enumerated list** of things to forbid or require, when what the author meant was a
**property** that must hold. The list is correct on the day it is written and wrong
the moment reality produces an item nobody enumerated. Every instance was found the
same way: something outside the list walked straight past the check.

**A-verify — the five claimed instances, checked against source.** Three did not
happen the way they were remembered, and the difference is the most encouraging
finding in this document.

| # | Claim | Verdict |
|---|---|---|
| 1 | `CLAUDE.md` rule 1: "no exceptions" → three named exemptions | **Holds** — `CLAUDE.md:35`, commit `1186fcc` |
| 2 | `CLAUDE.md` rule 2: "every index" → one index leading with the policy key | **Holds** — `CLAUDE.md:36`, commit `0ee4ba7` |
| 3 | `qual = 'true'` denylist → a positive claim-function rule | **Holds in substance — never committed** |
| 4 | `isPublishableKey()` denylist → allowlist | **Holds in substance — never committed** |
| 5 | `safeRedirectPath()` denylist → positive rule | **Holds in substance — never committed** |
| 6 | A locale test asserting on `document.documentElement.lang` | **Does not hold** |
| 7 | The `[A-Za-z]{3}` date regex, red every September | **Holds — already fixed** |

**Three of the five never reached `main`.** `git log --all -S'referencesClaim'` returns
only `dee21e2`, which created the file with the positive rule already in it;
`lib/supabase/keys.ts` was created whole by `b304947` with the allowlist already in
it; `safeRedirectPath`'s denylist survives only as prose in its own header
(`lib/api/boundary.ts:304-305`, recording that it *"refuses exactly one spelling of
the attack and honours at least five others"*). All three denylists were written,
caught in review, and replaced **before the commit**. What looked like four
consecutive shipped defects was two shipped (both in `CLAUDE.md`, both documentation)
and three caught by the loop that exists to catch them. That is the review working,
and it should be recorded as such.

**Claim 6 was mine, and it is wrong.** `document.documentElement.lang` appears
nowhere in the repository and in no commit in its history. The real defect at
`d2890ec` was different: copy switched to English at `98d6012` while
`components/shell/timezone.ts` kept `new Intl.DateTimeFormat("id-ID", …)`, so the
header read "27 Agu 2026" — and the test passed because, in that commit's own words,
*"the test named the same locale the code did — it agreed with the implementation
instead of checking it."* That is a **tautological assertion**, not an enumerated
list. Nothing was enumerated and nothing was missing from a list. The fix was also
not "restate as a property": it collapsed two values into one module and encoded the
relationship in the type system (`lib/locale.ts:16,24`), making the defect
*unrepresentable* rather than detectable. Two distinct root causes were being counted
as one.

The residual is worth keeping: `tests/browser/shell.test.tsx:1094-1098` computes its
expectation with `new Intl.DateTimeFormat(UI_LOCALE, { dateStyle: "medium" })` —
byte-for-byte what `components/shell/timezone.ts:47` does. Nothing asserts
`UI_LANG === "en"`. Set both constants back to Indonesian and the suite stays green.
The tautology moved up one level; it was not removed.

**Claim 7 holds and was the clearest case of the family.** Fixed at `dfd4ba5`, whose
message states the lesson exactly: *"Length was never the property — rejecting a
weekday prefix was."* Current form, `tests/browser/shell.test.tsx:1083`:
`/^\d{1,2} [A-Za-z]+ \d{4} · WIB$/`, with two siblings fixed alongside it.

**A-N12 — `public.tenant_id()`'s `stable` volatility is unasserted, and rule 3
depends on it.** **MEDIUM.** Verified: `provolatile` appears nowhere in
`tests/isolation/support/catalog.ts` or any isolation suite — the reader selects

`supabase/migrations/20260827000000_tenant_isolation_foundation.sql:95,123` and are

again — the exact 7.4x regression the wrapping rule exists to prevent, measured and
recorded in `catalog.ts`'s own comment — while every policy still reads
`(select …)` and the whole suite stays green. The rule is enforced on its *syntax*
and not on the property that makes the syntax work.

One line to close: add `p.provolatile` to the reader alongside `proparallel`, and
assert `'s'` for the claim functions exactly as `catalog-sweep.test.ts:316` already
does for parallel-safety. Folded into action item 3.

Queried against the live project on 2026-09-06: `anon` holds `EXECUTE` on roughly

**Severity: MEDIUM** — no live exposure, a real hole in the gate, and it sits in the

### Theme B — Substrate divergence: the container and the live project

Three occasions where the Postgres container the isolation suite runs against and
the live Supabase project disagreed about a default.

**B-1 — Supabase's `ALTER DEFAULT PRIVILEGES` grants `ALL` on every new table to
`anon` and `authenticated`.** The container does not. RLS still held, so no row
leaked — but the failure mode changed shape underneath the tests: what the suite
proved as *"refused by privilege"* was, live, *"filtered to zero rows."* Same
outcome today; different outcome the first time a policy has a gap.
Source: `supabase/migrations/20260828000000_explicit_privilege_surface.sql`, whose
whole existence is the fix. This was the first divergence where **Supabase was the
more permissive substrate** — the two earlier ones ran the other way, which is
what made it easy to miss.

**B-2 — CI never applies migrations to Supabase.** Debt entry 40. The isolation job
runs `npm run db:isolation:up` against a `postgres:17` container and nothing else.
Every divergence above was found by a human running a query by hand. That is the
mechanism by which B-1 was found, and it is not a mechanism.

**B-3 — The migration ledger and the repository agree, as of today.** Debt entry 45
recorded them disagreeing. Verified live 2026-09-06: five ledger rows —
`20260827000000_tenant_isolation_foundation` … `20260828000000_explicit_privilege_surface`
— matching the five files in `supabase/migrations/` name for name. **Resolved, and
the ledger entry never said so** (see Theme D).

**Checked and clean:** `ltree` is *not* a divergence. It is created by

### Theme C — Why the implementer's pushback was structural, not lucky

The implementer sub-agent contradicted the spec five times across Stories 1.5 and
1.6 and was right five times. That is worth understanding as a property of the
process, because a property can be kept and luck cannot.

The mechanism is a single field. **Every one of the seven story specs carries an
`Ask First:` line** naming the specific things the implementer must not decide
alone:

- `spec-1-1:25` — any dependency the starter did not install
- `spec-1-2:26` — editing any file under `components/ui/` by hand
- `spec-1-3:27` — any change to `--spacing` or the settled `--ui-*` contrast values
- `spec-1-4:25` — any new allowlisted exemption; any use of `service_role`, anywhere
- `spec-1-5:25` — any `security definer` function; any edit to an applied migration
- `spec-1-6:25` — enabling the hook on the live project; any *third* `security definer` function

That last one is the clearest case. The spec put "a third `security definer`
function" on Ask First; the founding-membership problem turned out to need exactly
that; the implementer stopped and asked instead of writing it. The decision reached
the owner, who chose it deliberately — recorded at `deferred-work.md:274`, and the
three functions live on the project today, all `search_path`-pinned and
`postgres`-owned, verified 2026-09-06.

**The lesson is transferable and it is cheap: a spec that names what the implementer
may not decide alone converts a silent wrong answer into a question.** The Ask First
line costs one sentence per story and it is the highest-yield sentence in the
document.

**Evidence limit, stated plainly:** the five pushbacks themselves happened in
conversation. The session transcripts were not read (see the inventory). What is
sourced above is the *mechanism* — the `Ask First` fields, and one decision whose
outcome the ledger records. The count of five rests on the session summary alone and
should be read as recollection, not as evidence.

### Theme E — Seams between stories

Findings from the boundary review, each re-verified by me against the primary
source before being routed. Two were checked by mutation, which is this project's
own standard of proof.

**E-1 — The ownership fallback renders one company's name over another company's
data.** `lib/auth/session.ts:214-245`. **HIGH.** Verified by reading the function.

`currentActiveCompany()` looks for the claim's tenant in the membership list. When
it is not there it does not fail closed — it falls through to `currentCompany()`,
which is keyed on `organizations.owner_user_id` and is entirely independent of the
tenant claim.

The scenario is a supported operation, not an edge case. A user owns organization
O_A → company **A**, and holds an active membership in company **B**. They switch to
B, so the token carries `tenant_id = B`. An admin of B then deactivates them —
`memberships.is_active = false`, which the migration documents as the designed
deactivation path taking effect on the next refresh
(`supabase/migrations/20260827160000_memberships_and_tenant_context.sql:276-279`).
For the remaining life of the token, up to 15 minutes:

- `switch_company(null)` filters on `is_active`, so the list is `[A]`
- `claims.tenantId` is still `B`, so `companies.find(B)` is `undefined`
- the fallback returns **A** — legal name, timezone, plan
- every row rendered below was filtered by RLS at `tenant_id() = B`

The header says PT A. The body is company B. And because `companies.length === 1`,
`components/shell/company-switcher.tsx:114-125` renders the non-interactive label
form, so the user has no control that could reveal the mismatch.

**What makes this the sharpest finding in the retrospective is the comment directly
above it.** `lib/auth/session.ts:199-204` says, in the author's own words, that
picking `companies[0]` *"would put one company's name over another company's data
for exactly as long as a token outlives a switch."* The hazard was seen, named, and
guarded — against **one enumerated way of reaching it**. The fallback reaches the
same state by a second route the guard never considered. This is Theme A at its
purest: a defence written against a list of known wrong answers rather than as the
property *"the company rendered is the company the claim names."*

**E-2 — Role and company can come from different tenants in the same header.**
`app/(app)/layout.tsx:54-72`. **MEDIUM.** Same root cause as E-1, second symptom.
`user.role` is read from `claims.role` (tenant B) while `company` came from the
ownership fallback (tenant A). In the E-1 scenario the header reads "PT A · HR
Staff", where `hr_staff` is the role in B and the real role in A is `admin`.
`membershipCount` is `companies.length`, a list that need not contain the company
being rendered — so with memberships in two other companies the pill becomes an
interactive menu listing B and C under the label "PT A", and the check mark lands
beside a company the header does not name.

**E-3 — `alter default privileges … revoke all on functions` is inert.**
`supabase/migrations/20260828000000_explicit_privilege_surface.sql:88`. **MEDIUM
today, HIGH the day a definer function ships without an explicit revoke.**

This is the root cause beneath finding A-live, and it is worse than a missing
assertion. The statement removes Supabase's *explicit* role grants but leaves
Postgres's own built-in default — `EXECUTE TO PUBLIC` — which `anon` and
`authenticated` are both members of. Reproduced on the isolation database against a
fresh schema: after the same grant-then-revoke, a new **table** is correctly
inaccessible to `anon`, and a new **function** is not.

So a function added by a future migration is born `anon`-executable and reachable
through PostgREST at `/rest/v1/rpc/<name>`. The file's own line 160 claims to be
"the complete statement of who may call what." It is a statement about five named
functions.

**And the guard test that exists is itself a denylist.**
`tests/isolation/catalog-sweep.test.ts:470-487` — *"leaves no default privilege that
would expose the NEXT table"* — matches `defaclacl like '%anon=%' or
'%authenticated=%'`. The PUBLIC entry is spelled `=X/postgres`, with no role name
before the `=`, so the pattern does not match, the test finds zero rows, and it
passes while the hazard is live. **A test written specifically to catch the next
occurrence of this class of bug misses it, because it too was written as a list of
spellings rather than as the property.**

Concretely, Story 1.7: `create function public.branches_in_scope(...) security
definer`, followed by `grant execute … to authenticated` and no `revoke … from
public`, ships callable by `anon` and the whole isolation suite stays green.

**E-4 — A failed switch reports failure and then happens anyway.**
`app/api/memberships/switch/route.ts:52-78`. **MEDIUM.**

`switchCompany()` commits `update memberships set last_active_at = now()` in its own
transaction. If the subsequent `refreshSession()` fails, the route returns 500 and
the switcher renders *"We could not switch company. You are still in PT A"*
(`components/shell/company-switcher.tsx:244`) without navigating. Nothing rolls back
or compensates the committed write.

Within 15 minutes the token expires; `proxy.ts` refreshes on the next navigation;
the hook re-runs and orders by `last_active_at desc`
(`20260827160000_...sql:296`) — which now points at **B**. The session silently
lands in company B, having explicitly told the user it had not moved. The route's
own comment (lines 32-36) anticipates the write surviving and concludes "the client
stays where it is and says so" — true until the next refresh, which is the thing
the comment does not consider.

**Seams checked and sound** — these were examined and no defect was found, which is
different from unexamined:

- **RLS vs privileged code paths.** No `service_role` client exists anywhere in
  `app/`, `lib/` or `scripts/`, and `tests/isolation-registration.test.ts:217-247`
  pins that for the CI workflow and every migration. No `set role` or `set_config`
  outside test harnesses. All three `SECURITY DEFINER` functions pin
  `search_path = ''`, fully qualify every reference, and take no user-identifying
  argument — `switch_company` and `create_founding_membership` both derive the
  subject from `public.auth_user_id()` and raise `28000` on null, and
  `create_founding_membership` restates the ownership check RLS would have made.
  Confirmed against `pg_proc.proconfig` live.
- **Table privileges.** `REQUEST_ROLE_PRIVILEGES` covers all three tables with
  exact-equality assertions; a relation with no entry fails outright; the negative
  control at `catalog-sweep.test.ts:496-545` proves the reader actually sees a table
  born under Supabase's default ACLs. The table half of the privilege work is sound
  — it is only the function half that is not.
- **Shell fixtures.** `SHELL_COMPANY_FIXTURE` and `SHELL_USER_FIXTURE` are
  unreachable from production code; the only importers are the browser suite.
  `PENDING_SHELL_COMPANY` is a real state, not a mock.
- **Token reissue.** Both mutating routes reissue and treat a failed reissue as a
  failed request. `tests/tenant-context-reissue.test.ts` enforces the rule for routes
  added later by walking `app/api/**/route.ts` per symbol.
- **Error leakage in the newest route.** `app/api/memberships/switch/route.ts` routes
  every cause to `logFailure` (lines 60, 66, 76) and returns `forbidden`/`serverError`,
  neither of which accepts a message derived from the cause. No Postgres text reaches
  a caller.
- **The AD-2 lint boundary.** `eslint.boundary.mjs:31` scopes to `lib/domain/**` by
  design — it is a purity rule about what the core may import, not a layering rule
  over `app/api` or `lib/auth`. Verified it still bites on files added by the last
  two stories, at both covered depths: a probe at `lib/domain/probe.ts` draws 3
  errors and one at `lib/domain/payroll/probe.ts` draws 2.

The architecture review reported that the zone-name mapping is duplicated between

### Theme G — The second root cause: tests that agree with the implementation

Separating this from Theme A is the most useful analytical move in this
retrospective, because the two look identical from a distance and take opposite
fixes. A **list** defect is fixed by restating the rule as a property. A
**tautology** is fixed by getting the expectation from somewhere other than the
code under test — or, better, by making the defect unrepresentable.

Five members, all verified:

**G-1 — `tests/isolation/write-surface.test.ts:240-258`, "the migrations can be
applied twice", never applies them twice.** **MEDIUM.** Proved by reading the body.
The comment states the hazard exactly right — *"a bare `alter table … add
constraint` raises 42710 the second time and takes the whole push down with it"* —
and the test then counts check constraints on two tables and asserts the count is
greater than zero. It asserts **that there is something to re-apply**, not that
re-applying works. Every `do $$ … if not exists` guard in every migration is
currently unverified, and the runbook that motivated the test ends in
`supabase db push`.

**G-2 — The locale test named the same locale the code did.** Fixed at `d2890ec`;
described under A-verify. The archetype of the family.

**G-3 — The off-palette test draws its probes from the rule's own list.**
`tests/theme.test.ts:1137-1148` probes five class names, every one of them from the
same 21 families `TAILWIND_PALETTES` enumerates. It can only ever confirm that the
listed families are listed. This is why A-N2 (`neutral`) survived.

**G-4 — The header-date test computes its expectation the way the code does.**
`tests/browser/shell.test.tsx:1094-1098` builds `new Intl.DateTimeFormat(UI_LOCALE,
{ dateStyle: "medium" })` — byte-for-byte `components/shell/timezone.ts:47`. And
nothing anywhere asserts `UI_LANG === "en"`. Set both constants back to Indonesian
and the whole suite stays green. The type-level fix at `lib/locale.ts` removed the
*disagreement* between two values; it did not add an assertion about what the value
**is**.

**G-5 — The theme storage key is only ever read through its own constant.** The
literal `"aira-theme"` appears exactly once in the repository, in
`app/theme-script.ts`. Every test imports `THEME_STORAGE_KEY`. Renaming the value
keeps every suite green and silently orphans every user's stored preference.

**The distinction that makes this actionable.** Theme A's fix is *"say what you
mean."* Theme G's fix is *"an assertion must have an independent source of truth."*
Three shapes qualify as independent: a literal written out in the test, a value
parsed from a different artefact than the one under test, or a negative control that
proves the assertion can fail. This project already does the third one extremely
well — `catalog-sweep.test.ts:636-713` carries a negative control for every isolation
rule, creating the offending table in a rolled-back transaction. **The technique that
would fix Theme G is already in this codebase, applied thoroughly in one suite and
almost nowhere else.**

## Open questions

**1. Should CI apply migrations to the live Supabase project, or should the container
be taught Supabase's defaults?** Every substrate divergence in this epic was found by
a human running a query by hand. `globalSetup.ts` already installs Supabase's default
ACLs into the container, which is the second answer applied once, reactively, after
the defect was found in production. A general answer would change how much the
isolation suite can be trusted. The trade is cost: `supabase start` is 541s and
~8.5GB against 31s and 161MB for bare Postgres. **A human answer changes item 3's
scope and the whole shape of Epic 5's testing.**

**2. Should acceptance criteria be written for security properties, or is the
adversarial review the right home for them?** Thirty-one unspecified behaviours
shipped, several security-critical. Writing criteria for them up front is the
textbook answer and would have specified none of them, because they were discovered
by attacking the code. The honest alternative is to say so: that `epics.md` specifies
*features* and the review specifies *defences*, and that auditing this product means
reading both. **This is a documentation-contract decision, not an engineering one.**

**3. Is `ltree` in `public` acceptable, given Story 1.7?** It puts ~60 unpinned
`supabase_admin` functions in the same schema as the app's security-relevant ones and
is flagged by Supabase's own linter. Moving it to `extensions` was deferred pending a
